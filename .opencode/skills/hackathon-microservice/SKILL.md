# Go-микросервис для хакатона 2une

## Сначала прочитай контракт

1. Прочитай `ONLINECONF_CONTRACT.md` в корне хакатонного репозитория. Он определяет маршруты, поля, правила rollout, роли команды и приёмку. Если согласованный контракт обновился, используй его вместо примеров из этого скилла.
2. Проверь, что уже есть в рабочем дереве: продуктовый бэкенд, фронтенд, Compose, админка. Если частей ещё нет, выясни, где команда собирает стенд и кто импортирует исходники. Не создавай дубликаты приложений и не подменяй ветку, выбранную командой.
3. Определи владельца участка. Сервис и схема БД, продуктовый Go, админская SPA и продуктовый фронт с выкладкой — четыре разные задачи. Если соседняя часть не готова, используй локальную фикстуру по контракту. Изменения стыка сначала согласуй с владельцем другой стороны.

## Что взять из Auth в `dev`

Референс — `origin/dev` исходного backend-репозитория [`go-park-mail-ru/2026_2_Na_Vse_200`](https://github.com/go-park-mail-ru/2026_2_Na_Vse_200). Это отдельный репозиторий, поэтому `origin/dev` нового хакатонного репозитория может не содержать этот код. Для просмотра используй `git show origin/dev:<путь>` в исходном checkout или соответствующую ветку на GitHub.

| Путь в бэкенде | Что посмотреть |
| --- | --- |
| `auth-microservice/cmd/auth/main.go` | Отдельная точка входа для процесса, запуск и проверка работоспособности. |
| `auth-microservice/internal/app/auth.go` и `auth-microservice/internal/config/config.go` | Как собираются зависимости, читается окружение и завершается сервис. |
| `Dockerfile` и `compose.yaml` | Как собирается отдельный бинарник и запускается отдельный контейнер; как Compose связывает готовность и внутренний адрес. |
| `internal/app/auth_client.go` | Как продуктовый процесс инкапсулирует обращение к соседнему сервису. |

Переноси схему подключения: **свой процесс → свой контейнер → внутренний адрес → клиент в продукте**. OnlineConf использует HTTP/JSON; не переносить gRPC, protobuf или сам Auth ради сходства. Отдельному процессу не обязательно иметь отдельный Go-модуль или сервер БД.

## Реализация по участкам

### Сервис OnlineConf

- Добавь отдельный Go entrypoint, например `cmd/onlineconf`, в согласованном каталоге сервиса. Подключи параметры через окружение, конечные таймауты HTTP, проверку готовности и завершение по контексту.
- Храни записи в таблицах OnlineConf в PostgreSQL. Переиспользуй уже подключённый драйвер там, где его разрешает контракт, параметризуй SQL. Согласуй владельца и способ запуска миграции; Compose должен дождаться её успешного завершения. Не меняй применённые миграции.
- Начни с `GET /internal/v1/entries`, `PUT /internal/v1/entries/{scope}/{key}` и `GET /internal/v1/snapshot`. `PUT` создаёт или обновляет запись по паре `scope + key`, но не меняет её `kind`. Снимок возвращает `{"entries":[...]}`. Валидацию JSON, процента и списков UUID возьми из контракта. Проверь, что JSON `null` отличается от отсутствующего `value`.
- Не добавляй сторонние библиотеки, npm-пакеты и Go-зависимости. Используй стандартную библиотеку Go, существующий доступ к PostgreSQL и инструменты проекта.

### Продуктовый Go

- Используй существующую сессию и серверный список UUID администраторов. Права проверяются при доступе к административному разделу и при каждом запросе к `/api/v1/admin/onlineconf/*`; для записей переиспользуй CSRF. Внутренние запросы формируй на сервере: не пересылай браузерные cookie, CSRF и утверждения клиента о личности администратора.
- Попробуй загрузить снимок сразу, затем обновляй его каждые **10 секунд** с таймаутом. Запросы пользователя читают память; успешный валидный снимок целиком заменяет старый, ошибка оставляет последний рабочий. До первой успешной загрузки и для отсутствующих ключей сохраняй продуктовые дефолты.
- Примени `catalog/popular_tracks_limit` и `catalog/popular_tracks_enabled` в `GET /api/v1/home`. Верни `popular_tracks` и эффективные настройки в `online_conf`. Сохрани прежний массив `tracks` для очереди плеера. Не отдавай браузеру сырой снимок и UUID из исключений; для персонализированного ответа используй `Cache-Control: private, no-store`.
- Вычисляй флаг в одном месте: `enabled: false` отключает для всех, затем при `enabled: true` работают `force_off` и `force_on`, после них стабильная группа на `hash/fnv` от `scope/key/userID`. Для авторизованного используй UUID из проверенной сессии; гость видит блок только при 100% у включённого флага. Источник истины для этих правил — контракт.

### Админка, фронт и выкладка

- Разворачивай админку отдельной Vite-сборкой с базовым путём `/admin/`, на том же домене, что продукт. Используй существующие MyReact, TypeScript и `requestJson` с cookie и CSRF. Проверь прямой переход и обновление `/admin/`: продуктовый SPA fallback и service worker не должны подменять админский HTML.
- В Compose запускай OnlineConf отдельно в приватной сети. Продуктовый сервер обращается по внутреннему DNS-имени сервиса, например `http://onlineconf:8090`. Не публикуй порт OnlineConf: браузер обращается к защищённому продуктовому API. Проверь запуск из согласованной сборки и доступность административного маршрута на реальном домене.
- На продуктовой главной рендери `popular_tracks` по `online_conf`; пустой массив допустим и не означает, что надо брать очередь плеера. При старом ответе без новых полей оставь прежнее поведение. Сначала подключи ответ-фикстуру, потом реальный `/home`.

## Приёмка

1. Подними Compose и проверь готовность: продукт получает снимок внутри сети, `/` и `/admin/` открываются на одном домене, OnlineConf не имеет публичного порта. Проверь `401` гостя, `403` обычного аккаунта и отказ записи без CSRF.
2. Создай в админке конфиг и флаг, найди их по имени и scope. Проверь, что можно сохранить массив и что процент `101` отклоняется. Измени лимит с `6` на `3`, засекши время от успешного PUT до нового ответа `/home`. При достаточном каталоге в API и UI три популярных трека, очередь плеера не меняется; задержка не превышает 60 секунд на здоровом стенде.
3. На двух аккаунтах проверь `0% + force_on`, `100% + force_off` и глобальное отключение. При сбое загрузки снимка проверь сохранение последней рабочей версии.
4. Выполни `go test ./...` в затронутых Go-модулях, сборку обеих SPA и имеющиеся проверки типов/линта для затронутого фронта. Укажи изменённые файлы, команды и результат, отдельно — что не запускалось. Не делай коммит, push или деплой без прямого поручения.
