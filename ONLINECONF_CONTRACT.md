# OnlineConf для 2une

Контракт для согласования командой. Цель MVP — менять настройки музыкального сайта через отдельную админку без пересборки и деплоя. В штатном режиме изменения должны применяться на продуктовом бэкенде не позднее чем через 60 секунд после успешного сохранения.

## 1. Кто что делает

| Участник | Зона ответственности | С чего начать | Критерий готовности |
| --- | --- | --- | --- |
| Бэк №1 | Сервис OnlineConf, PostgreSQL, миграция, внутренние ручки списка, сохранения и снимка | Согласовать JSON из разделов 4–5. Написать модели, миграцию и обработчики. До готовности БД дать бэку №2 статический снимок для локального мока | Можно создать и изменить конфиг или флаг, найти его по ключу и scope, получить актуальный снимок |
| Бэк №2 | Интеграция в продуктовом Go API: сессии, права, CSRF, клиент OnlineConf, кеш, rollout и изменение `/home` | Подключить клиент к мок-снимку. Параллельно реализовать вычисление флага и расширить DTO главной | Настройка из админки меняет ответ `/home`; обычному пользователю административный API отвечает отказом |
| Фронтендер | Вся отдельная SPA админки: вход в экран, список, фильтры, обе формы, ошибки, подключение HTTP | Сделать экран на моках по контракту. Собрать отдельный Vite-билд с `base: '/admin/'` | Админ из браузера создаёт, находит и редактирует обе записи. Гость и обычный пользователь видят соответствующее состояние доступа |
| Фулстек | Продуктовый фронт, маршруты стенда, сборка и сквозное демо | Подключить мок `/home` к главной. Параллельно настроить на стенде раздачу двух сборок и адрес внутреннего сервиса | На одном домене работают сайт и админка. Изменение лимита и раскатки можно показать на стенде двумя аккаунтами |

Бэк №1 владеет схемой OnlineConf и его миграциями. Бэк №2 владеет маршрутизацией продуктового Go API и изменениями `/home`. Фронтендер владеет исходниками админки. Фулстек владеет продуктовой главной и конфигурацией выкладки. Изменение контракта сначала согласуют владельцы обеих сторон стыка.

## 2. Архитектура

```text
Браузер → /admin/ → отдельная SPA OnlineConf
                    ↓ запросы /api/v1/admin/onlineconf/...
Продуктовый Go API → проверка сессии, прав и CSRF → сервис OnlineConf → PostgreSQL
        ↑
        └── внутренний снимок каждые ~10 секунд → кеш в памяти Go API

Музыкальная SPA → GET /api/v1/home → Go API применяет кеш к текущему пользователю
               ← каталог, popular_tracks и эффективные значения настроек
```

- Две SPA имеют разные точки входа и отдельные сборки. Основная доступна по `/`, админка по `/admin/`. Прямой переход и обновление страницы админки открывают её HTML. Префикс `/api/` обслуживается Go API.
- Админка использует существующую сессию 2une. Продуктовый Go API ограничивает доступ к админскому разделу и проверяет права на **каждом** запросе к административному API. Для MVP список UUID администраторов задаётся в серверной конфигурации. Гость получает `401`, вошедший пользователь без прав — `403`. Для самого экрана можно отдать страницу входа или отказ согласно принятой на стенде схеме.
- OnlineConf — отдельный процесс или контейнер. Его внутренний HTTP-адрес доступен продуктовому сервису в приватной сети. Админские операции и снимки передаются через внутренний API. Cookie и CSRF-токен проверяет продуктовый Go API, идентификатор администратора при необходимости передаётся между сервисами из проверенной сессии.
- PostgreSQL — источник сохранённых настроек. Продуктовый Go API читает настройки из кеша в памяти. При запуске он запрашивает снимок и дальше обновляет его раз в 10 секунд. На запрос пользователя приходится чтение кеша. Снимок заменяется целиком после успешной загрузки и проверки, при временном сбое продолжает действовать предыдущий. До первого снимка, а также для отсутствующих ключей используются продуктовые значения по умолчанию.
- Значения `/home` зависят от пользователя, поэтому промежуточные HTTP-кеши не должны выдавать ответ одного аккаунта другому. Для MVP продуктовый API отдаёт `Cache-Control: private, no-store`. Если музыкальная SPA сохраняет каталог для офлайна, она использует существующее разделение кеша по пользователю и при доступной сети берёт свежий ответ.

## 3. Правила реализации

**Сторонние библиотеки для OnlineConf запрещены.** Не добавляем npm-пакеты или Go-модули и не копируем код сторонних библиотек. Разметка и формы — на существующем MyReact, TypeScript и браузерных API. HTTP-клиент — существующий `requestJson` с поддержкой cookie и CSRF. На бэке — стандартная библиотека Go, существующие обработчики сессии и CSRF, принятый в проекте слой доступа к PostgreSQL. Существующие Vite, TypeScript, ESLint и уже подключённый драйвер БД используются в их текущей роли. Новый UI-фреймворк, клиент HTTP, роутер, пакет раскатки, ORM или внешняя платформа флагов не нужны.

- Соблюдаем структуру проекта. На Go обработчик работает с HTTP и DTO, use case содержит правила, repository отвечает за SQL. Запросы параметризованы, изменения схемы идут миграцией. На фронте API-клиент и типы отдельно от представления, обработчики с логикой названы и вынесены из JSX, стили следуют принятому БЭМ.
- Для запросов с изменениями браузер получает токен через `GET /api/v1/auth/csrf` и отправляет `X-CSRF-Token`. Права и UUID текущего пользователя берутся из серверной сессии. Списки исключений и правила раскатки доступны только администратору.
- Каждому участнику своя ветка от общей согласованной базы и небольшой PR по своей зоне. Общие изменения контракта обсуждаются до реализации. Проверки перед интеграцией: сборка обеих SPA, проверка типов и ESLint по скриптам проекта, `go test ./...` в Go-модулях.

## 4. Формат записей и API админки

`scope` — область применения, например `catalog` или `frontend`. Поиск фильтрует по вхождению `q` в имя `key` без учёта регистра. Scope фильтруется по точному совпадению. Для имён scope и key используем строчные латинские буквы, цифры, `_` и `-`; имя начинается с буквы. Пара `scope + key` определяет запись. При редактировании тип и имя записи сохраняются.

| Запрос браузера | Ответ |
| --- | --- |
| `GET /api/v1/admin/onlineconf/entries?scope=catalog&q=popular` | `200`, тело `{"entries":[...]}`. Оба фильтра необязательны. Пустой результат — `{"entries":[]}`. Сортировка по `scope`, затем по `key`. |
| `PUT /api/v1/admin/onlineconf/entries/{scope}/{key}` | `200`, тело — полная сохранённая запись вместе с `scope` и `key`. Первый PUT создаёт запись, последующие обновляют её. |

Сервис OnlineConf предоставляет продуктовому Go API те же операции по внутренним путям `GET /internal/v1/entries` и `PUT /internal/v1/entries/{scope}/{key}`. Запросы используют те же фильтры, тела и ответы. Для фонового обновления кеша предусмотрен отдельный `GET /internal/v1/snapshot`, ответ `200` с полным `{"entries":[...]}`, без фильтров.

Тело PUT для конфига:

```json
{"kind":"config","value":3}
```

Поле `value` обязательно. Общий формат допускает объект, массив, строку, число, булево значение и `null`. Для продуктового ключа `catalog/popular_tracks_limit` допустимо только целое число от 1 до 20. Список и ответ PUT содержат также поля `scope` и `key`.

Тело PUT для флага:

```json
{
  "kind": "flag",
  "enabled": true,
  "rollout_percent": 25,
  "force_on": ["11111111-1111-4111-8111-111111111111"],
  "force_off": []
}
```

Все поля в теле флага обязательны. Процент — целое от 0 до 100. Для исключений принимаются массивы UUID. Пустые списки передаются как `[]`. Пересечения списков запрещаем при сохранении. При чтении снимка `force_off` имеет приоритет на случай пересечения в ранее сохранённых данных.

```json
{"error":{"code":"validation_failed","message":"Проверьте поля","fields":{"rollout_percent":"Введите целое число от 0 до 100"}}}
```

| Ситуация | HTTP и код |
| --- | --- |
| Ошибка полей или JSON | `400 validation_failed` |
| Нет действующей сессии | `401 unauthorized` |
| Нет прав администратора | `403 forbidden` |
| CSRF-проверка отклонила запись | `403 csrf_rejected`, код существующего middleware |
| Попытка изменить `kind` существующей записи | `409 kind_conflict` |
| Онлайн-сервис недоступен для административной операции | `503 onlineconf_unavailable` |

Фронтендер делает формы на этом контракте. Для JSON достаточно текстового поля и `JSON.parse` перед отправкой. Для флага подходят два текстовых поля со списками UUID, по одному ID в строке. После PUT экран показывает успех и перечитывает список с текущими фильтрами. При ошибке форма сохраняет введённые значения.

## 5. Продуктовый контракт и расчёт флага

Для демо используем scope `catalog` и блок «Популярные треки». Существующий массив `tracks` используется в очереди плеера, поэтому под изменяемый блок выделен отдельный массив `popular_tracks`.

| Ключ | По умолчанию | Как применяется |
| --- | --- | --- |
| `popular_tracks_limit` | `6` | Бэк ограничивает количество элементов в `popular_tracks` настроенным числом и доступным количеством треков. Фронт использует значение как предел при отображении. |
| `popular_tracks_enabled` | `true` при отсутствии записи | Бэк вычисляет доступность для текущего пользователя и отдаёт пустой `popular_tracks`, если блок выключен. Фронт скрывает всю секцию. |

Расширяем существующий `GET /api/v1/home`. `tracks`, `artists`, `albums` остаются частью контракта. Пример ответа для пользователя, у которого блок выключен:

```json
{
  "tracks": [],
  "artists": [],
  "albums": [],
  "popular_tracks": [],
  "online_conf": {
    "popular_tracks_limit": 3,
    "popular_tracks_enabled": false
  }
}
```

При включённом блоке `popular_tracks` содержит объекты того же формата, что и `tracks`. Продуктовый фронт переносит новые поля из API-клиента до компонента главной. Для старого ответа без новых полей применяет текущие шесть карточек и видимый блок. Пустой `popular_tracks: []` в новом ответе считается корректным результатом.

Правила вычисления уже заведённого флага:

1. При `enabled: false` результат `false` для всех.
2. При `enabled: true` сначала проверить `force_off`, затем `force_on`.
3. Для остальных вошедших пользователей вычислить стабильную группу 0–99 из хеша `scope/key/userID`, используя стандартный `hash/fnv` в Go. Флаг включён, если группа меньше `rollout_percent`.
4. Для гостя включённый флаг доступен при раскатке 100%. Фронт получает результат от бэкенда и применяет его как булево значение.

Кеш бэка обновляется независимо от браузера. В обязательном демо после сохранения повторно открываем главную или обновляем вкладку. Дополнительное обновление без перезагрузки можно реализовать поверх существующей загрузки каталога, например раз в 15 секунд в открытой главной.

## 6. Сквозная приёмка

1. На стенде доступны `/` и отдельная сборка `/admin/`. У админа открывается список. У гостя и обычного пользователя прямые административные GET и PUT не проходят серверную проверку доступа.
2. Админ создаёт и находит через поиск конфиг и флаг в `catalog`. Отдельно создаёт запись в `frontend` и проверяет фильтр по scope. Пробует сохранить невалидный JSON и процент 101, ошибки видны в форме.
3. При включённом для всех флаге админ меняет лимит 6 → 3. Измеряем время от ответа PUT до первого нового ответа `/home`. В пределах минуты ответ отдаёт лимит 3 и максимум три популярных трека. При достаточном каталоге главная показывает ровно три карточки.
4. Админ оставляет `enabled: true`, ставит раскатку 0% и добавляет одного тестового пользователя в `force_on`. Для него блок показывается, для второго скрывается. Затем проверяем `force_off` при раскатке 100% и глобальное выключение. Прямой запрос `/home` показывает тот же результат.
5. После изменения настроек работают очередь плеера, блоки исполнителей и альбомов. По обычному запросу `/home` продуктовый сервис берёт конфиг из памяти.

После рабочего MVP приоритет допов: история изменений, проверка флага для заданного пользователя, затем обновление открытой главной без перезагрузки.
