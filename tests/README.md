# Тесты

Покрытие и состав тестов бэкенда. Требование РК1 — **не ниже 50%**.

Тестовые файлы лежат рядом с кодом, который проверяют: в Go тест обязан находиться
в том же пакете, иначе он не получит доступ к непубличным функциям. Эта папка —
только документация.

## Что проверяется

### `internal/handlers` — HTTP-ручки

Запросы отправляются через `httptest.NewRequest` и `httptest.NewRecorder`, то есть
без поднятия настоящего сервера. Хранилища подставляются реализациями в памяти,
а для проверки отказов — подменными, которые всегда возвращают ошибку.

- **Регистрация:** успех с кодом `201` и сессионной cookie; занятый email даёт `409`;
  битый JSON и пустое тело — `400`; невалидные поля — `400` с разбором по полям;
  email в другом регистре считается тем же аккаунтом.
- **Ответ не содержит пароля:** тело ищется на подстроки `password`, `sha256` и сам
  пароль — тест падает, если хоть одна найдена.
- **Выданная cookie рабочая:** после регистрации идентификатор из cookie ищется
  в хранилище сессий и должен указывать на того же пользователя.
- **Вход:** успех с новой cookie; неверный пароль и неизвестный email дают
  **побайтово одинаковый** ответ — тест сравнивает тела между собой; правила состава
  пароля на входе не применяются.
- **Полный цикл сессии:** регистрация → `/me` отдаёт того же пользователя → выход →
  `/me` с той же cookie отдаёт `401`.
- **Все отказы `/me` одинаковы:** четыре случая — нет cookie, сессия неизвестна,
  сессия истекла, пользователь удалён — сравниваются друг с другом.
- **Сбой хранилища не маскируется:** недоступное хранилище даёт `500`, а не `401`,
  и технические подробности в ответ не попадают.
- **Маршрутизация:** неизвестный путь — `404` в JSON, чужой метод — `405`
  с сохранённым заголовком `Allow`.

### `internal/handlers` — главная страница

- Успешный ответ: код `200`, заголовок `Content-Type`, три непустых массива.
- Карточка трека приходит собранной: есть идентификатор, название, положительная
  длительность и хотя бы один исполнитель.
- **Пустой каталог отдаёт `[]`, а не `null`.** Хранилище в тесте возвращает срезы
  `nil`, и тест проверяет, что в теле нет ни одного `null` — контракт требует массив,
  а `json.Marshal` превращает nil-срез именно в `null`.
- Недоступное хранилище каталога даёт `500` без технических подробностей.
- Главная отдаётся только по `GET`, на `POST` приходит `405`.
- Дата релиза приводится к UTC: время в другом часовом поясе не должно уезжать
  на сутки. Неизвестная дата приходит как `null`.

### `internal/repository/memory` — хранилища

- **Пользователи:** создание проставляет идентификатор и дату; поиск по
  идентификатору и по email; повтор email даёт `ErrEmailTaken`; отменённый контекст
  прерывает операцию.
- **Одновременная регистрация:** пятьдесят горутин создают один и тот же email,
  успешной обязана быть ровно одна.
- **Сессии:** создание и чтение; неизвестная даёт `ErrSessionNotFound`; просроченная
  даёт `ErrSessionExpired` **и удаляется** — повторное чтение возвращает уже
  «не найдено»; удаление несуществующей ошибкой не считается.
- **Каталог:** выдача треков, исполнителей и альбомов для главной страницы;
  предел выдачи не ломает ответ — ноль и отрицательное дают пустой список,
  слишком большое значение отдаёт всё, что есть.

### `pkg/validation` — проверки полей

Табличные тесты на email, пароль и имя: граничные длины, отсутствие `@`, точка
на краю домена, пароль без цифры, слишком короткий и слишком длинный.

Проверяется, что сессионная cookie при фронтенде на отдельном адресе уходит
с `SameSite=None` **и** `Secure`: без второго флага браузер молча выбрасывает первую.
И что аватар приходит строкой, когда он есть, и `null`, когда его нет.

Отдельно проверяется, что **минимальная длина пароля считается в символах,
а максимальная в байтах** — иначе пароль из шести кириллических букв проходил бы
как достаточно длинный, потому что весит одиннадцать байт.

Проверяется обрезка пробелов по краям пароля — одинаковая при регистрации и входе,
иначе случайно скопированный пробел закрыл бы доступ к созданному аккаунту.

И что проверки возвращают именно объявленные причины отказа, различимые
через `errors.Is`, а не текстом.

### `internal/auth` — пароли и сессии

- Один и тот же пароль проходит проверку после хеширования.
- Два хеша одного пароля **различаются** — поймает, если кто-то захардкодит соль.
- Пароль длиннее 72 байт отклоняется с `ErrPasswordTooLong`.
- Испорченный хеш не принимается за верный пароль **и** даёт ошибку: пустая строка,
  обычный текст, обрезанный хеш, хеш от другой схемы.
- Два вызова генератора идентификатора сессии дают разные значения.
- Хешер с ценой по умолчанию работает: пароль хешируется и проходит проверку.
  Этот тест один на весь пакет — на боевой цене один хеш считается около ста
  миллисекунд, поэтому остальные берут `NewBcryptHasherWithCost(MinCost)`.

### `internal/middleware` — обвязка

- Паника в обработчике не роняет процесс: клиент получает `500` в формате контракта,
  текст паники клиенту не уходит, а стек и идентификатор запроса попадают в лог.
- CORS: разрешённый origin получает заголовки, посторонний — нет; `Allow-Origin`
  не равен звёздочке, потому что она несовместима с передачей cookie.
- Идентификатор запроса: присланный клиентом переиспользуется, если это валидный
  UUID, иначе генерируется новый.
- Текстовые `404` и `405` от маршрутизатора подменяются на JSON.
- Обработчик, написавший тело без явного кода состояния, логируется как `200`:
  код подставляет стандартная библиотека, и обёртка обязана его заметить.
- Чтение идентификатора запроса из контекста, где его нет, даёт пустую строку,
  а не панику.

### `internal/config` — настройки

Значения по умолчанию; чтение из окружения; неразбираемое значение роняет старт,
а не подставляет значение по умолчанию; заданный `APP_ALLOWED_ORIGIN` без
`APP_COOKIE_SECURE=true` считается ошибкой конфигурации.

### `pkg/response` — запись ответов

Код состояния, заголовок `Content-Type`, формат ошибки с разбором по полям и без него.

Отдельно — данные, которые не сериализуются: клиент получает `500` и **пустое тело**,
а не половину JSON. Тело собирается целиком до отправки заголовков, поэтому отказ
ещё можно превратить в корректный ответ.

Остальное покрыто. Ветки, оставшиеся без прогона внутри покрытых функций, — это
обработка ошибок, которые не воспроизвести на хранилище в памяти: например, запись
в закрытое соединение. Они появятся в поле зрения, когда подключим PostgreSQL.

## Как запустить

```
go test ./...                 # прогон
go test ./... -cover          # с покрытием по пакетам
go test ./... -v              # с именами тестов
```

Общая цифра и разбор по функциям:

```
go test ./... -coverprofile=cover.out
go tool cover -func=cover.out          # таблица по функциям, последняя строка — итог
go tool cover -html=cover.out          # наглядно в браузере: что покрыто, что нет
```

Отдельный пакет или отдельный тест:

```
go test ./internal/handlers/ -cover
go test ./internal/handlers/ -run TestSessionLifecycle -v
```

Файл `cover.out` в репозиторий не коммитится — он в `.gitignore`.

## Принципы, которых держимся

**Проверяем поведение, а не отсутствие падения.** Тест смотрит, какой код состояния
вернулся и что записалось в хранилище, а не «не 500 — и ладно».

**Не тестируем чужие библиотеки.** Проверять, что bcrypt выдаёт строку из
60 символов, — это тест bcrypt, а не нашего кода. Проверяем то, что могли сломать сами.

**Зависимости подменяются через интерфейсы.** Обработчики получают хранилища
снаружи, поэтому в тесте вместо реализации в памяти подставляется подделка,
которая всегда возвращает ошибку. Так проверяются ветки, которые иначе не
воспроизвести.

**Таблица — когда случаев больше трёх и они однотипные.** Для четырёх значений
достаточно среза строк.
