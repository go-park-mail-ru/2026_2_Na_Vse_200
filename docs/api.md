## 1. Общие правила

- Базовый путь: **`/api/v1`**. Версия в пути, чтобы потом не ломать фронт.
- Тело запроса и ответа — всегда JSON. Заголовок ответа: `Content-Type: application/json; charset=utf-8`.
- Запрос с телом обязан слать `Content-Type: application/json`.
- Размер тела запроса ограничен 1 МБ; при превышении — `400 invalid_json`.
- Все адреса, кроме `/health`, живут под `/api/v1`.
- Неизвестный путь — `404 not_found`, неподдерживаемый метод — `405 method_not_allowed`,
  оба в общем JSON-формате ошибки (не текстом).
- Сервер валидирует все входные данные **независимо** от проверок на клиенте.
- Пароль не передаётся в query-строке и не пишется в логи.

### Таблица кодов ответа

| Код | Когда |
|---|---|
| 200 | успех с телом |
| 201 | создан объект (регистрация) |
| 204 | успех без тела (выход) |
| 400 | не разобрался JSON **или** не прошла валидация полей |
| 401 | нет сессии, сессия истекла, неверные учётные данные |
| 404 | адрес не найден |
| 405 | метод не поддерживается этим адресом |
| 409 | конфликт: email уже занят |
| 500 | ошибка на нашей стороне |

Решение команды: **на невалидные поля отвечаем 400, а не 422** — так в таблице кодов лекции.
Отличить «битый JSON» от «данные не прошли проверку» фронт может по `error.code`.

### Формат ошибки

Один формат на всё API:

```json
{
  "error": {
    "code": "email_taken",
    "message": "Пользователь с таким email уже существует"
  }
}
```

При ошибках валидации добавляется объект `fields` — ключ это имя поля из запроса:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Проверьте правильность заполнения полей",
    "fields": {
      "email": "Некорректный email",
      "password": "Пароль должен быть не короче 8 символов"
    }
  }
}
```

- `code` — машинный, по нему фронт ветвит логику. Список ниже закрытый, новые коды добавляются
  в этот документ.
- `message` — человекочитаемый текст на русском, можно показывать пользователю.
- `fields` — присутствует только при `validation_failed`.
- Внутренние детали (SQL, стектрейсы, пути) клиенту **не** уходят никогда: они пишутся в лог сервера,
  а клиент получает `internal_error` с общим текстом.

### Справочник `error.code`

| code | HTTP | Значение |
|---|---|---|
| `invalid_json` | 400 | тело не разобралось, не JSON, пустое тело, превышен размер |
| `validation_failed` | 400 | JSON разобран, но поля не прошли проверку; есть `fields` |
| `email_taken` | 409 | email уже зарегистрирован |
| `invalid_credentials` | 401 | неверный email **или** пароль (одинаково для обоих случаев) |
| `unauthorized` | 401 | нет cookie, сессия неизвестна или истекла |
| `not_found` | 404 | адрес не существует |
| `method_not_allowed` | 405 | адрес существует, метод не поддерживается |
| `internal_error` | 500 | любая внутренняя ошибка |

## 2. Сессия и cookie

Схема: сессии, не JWT. После входа сервер выдаёт непрозрачный случайный идентификатор,
сохраняет связь «идентификатор → пользователь» на своей стороне и кладёт идентификатор в cookie.
Клиент ничего не разбирает и не хранит сам — cookie ездит автоматически.

**Где хранятся сессии к РК1: в памяти процесса backend** — мапа `session_id → сессия` под
`sync.RWMutex` (каждый запрос обрабатывается в своей горутине, без блокировки это гонка).
Просроченные записи удаляются при чтении, чтобы мапа не росла бесконечно.

Почему так: сессия — не бизнес-сущность, в схеме БД её нет, Фёдору по ней работы нет.
Ни Redis, ни новой таблицы к 7 октября не нужно. Платим за это одним: **при перезапуске сервера
все сессии теряются**, поэтому перед показом сервис не передеплоивается. Требование
«сессия переживает перезагрузку браузера» при этом выполняется — речь про браузер, не про сервер.

В РК2 хранилище переезжает в Redis вместе с состоянием плеера (`playback_state` в схеме Фёдора).
Переезд стоит одной новой реализации `SessionStorageInterface` и одной строки в `main.go`:
ни контракт, ни обработчики, ни тесты не меняются.

| Параметр | Значение | Почему |
|---|---|---|
| Имя | `session_id` | |
| Значение | 32 случайных байта из `crypto/rand`, `base64.RawURLEncoding` | `math/rand` предсказуем, сессию можно подобрать |
| `Path` | `/` | cookie нужна всем ручкам |
| `HttpOnly` | `true` | JavaScript не прочитает — защита от XSS |
| `Secure` | `true` на стенде, `false` локально | по `http://` cookie с `Secure` не поедет; берётся из конфигурации |
| `SameSite` | `Lax` при одном origin, `None` при разных | `None` требует `Secure`: без него браузер выбрасывает cookie молча, поэтому сервер с таким сочетанием настроек не стартует |
| Срок жизни | 24 часа, задаётся конфигурацией | без явного срока cookie умирает с вкладкой, а требование РК — переживать перезагрузку |

Правила:
- Выход удаляет сессию **на сервере** и гасит cookie (`MaxAge: -1`). Погасить только cookie мало:
  идентификатор остался бы рабочим.
- Истёкшая, неизвестная и отсутствующая сессия дают **одинаковый** ответ `401 unauthorized`.
- Ошибка хранилища при проверке сессии — это `500 internal_error`, а **не** 401. Иначе падение базы
  выглядит для фронта как «пользователь разлогинился».
- Фронт обязан слать запросы с `credentials: 'include'`, иначе браузер не приложит cookie.

## 3. CORS

Нужен, если фронт и API окажутся на разных адресах. Предпочтительная схема стенда — один origin
с API под `/api/`, тогда CORS не нужен вовсе.

Если origins разные, сервер отдаёт:

```
Access-Control-Allow-Origin: https://<точный адрес фронта>
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: Content-Type
```

- `Allow-Origin: *` несовместим с `Allow-Credentials: true` — cookie ходить не будут.
  Указывается точный origin из конфигурации.
- На preflight-запрос `OPTIONS` сервер отвечает `204` без тела.

## 4. Модели ответа

ID во всех ответах — **строка**. Тип ключа в схеме БД ещё не зафиксирован (число или UUID),
а строка переживёт любой выбор; плюс в JavaScript целые числа больше 2^53 теряют точность.

### User

```json
{
  "id": "42",
  "email": "andrey@example.com",
  "display_name": "Андрей",
  "avatar_url": null
}
```

Хеш пароля и соль не отдаются никогда, ни при какой ошибке.
`avatar_url` — строка или `null`.

### Track

```json
{
  "id": "1001",
  "title": "Летний дождь",
  "duration_ms": 214000,
  "cover_url": "https://cdn.example.com/covers/1001.jpg",
  "artists": [ { "id": "7", "name": "Кино" } ]
}
```

`duration_ms` в базе лежит в `media_file.duration_ms`, а не в `track` — приходит джойном.
`artists` — массив, у трека может быть несколько исполнителей; пустым не бывает.
`cover_url` может быть `null`, фронт показывает заглушку.

### Artist

```json
{
  "id": "7",
  "name": "Кино",
  "image_url": "https://cdn.example.com/artists/7.jpg"
}
```

### Album

```json
{
  "id": "300",
  "title": "Группа крови",
  "release_date": "1988-08-01",
  "cover_url": "https://cdn.example.com/albums/300.jpg",
  "artists": [ { "id": "7", "name": "Кино" } ]
}
```

`release_date` — строка `YYYY-MM-DD` или `null`.

## 5. Правила валидации

Одинаковые на клиенте и на сервере. Клиентские проверки — для удобства пользователя,
серверные — обязательны.

| Поле | Правило | Текст ошибки |
|---|---|---|
| `email` | обрезаются пробелы, приводится к нижнему регистру; 3–254 символа; ровно одна `@`; непустая часть до и после; в домене есть точка | «Некорректный email» |
| `password` | не короче 8 символов и не длиннее 72 байт; есть хотя бы одна буква и одна цифра; пробелы по краям не обрезаются | «Пароль должен быть не короче 8 символов», «Пароль слишком длинный», «Пароль должен содержать хотя бы одну букву и одну цифру» |
| `display_name` | обрезаются пробелы; 2–50 символов; не только пробелы | «Имя должно содержать от 2 до 50 символов» |

Минимальная длина считается в символах, максимальная — в байтах: bcrypt отбрасывает всё
после 72 байт, поэтому предел задан в них. В символах он получается разным — для кириллицы
вдвое меньше, — и точное число пользователю не называется.

Если невалидных полей несколько, в `fields` приходят **все** сразу — фронт подсвечивает их за один раз.

## 6. Ручки

### 6.1 `POST /api/v1/auth/signup` — регистрация

Создаёт аккаунт и **сразу выполняет вход**: в ответе приходит сессионная cookie, на форму входа
пользователя вести не нужно — фронт ведёт его на главную уже авторизованным.

Запрос:

```json
{
  "email": "andrey@example.com",
  "password": "muzyka2026",
  "display_name": "Андрей"
}
```

Ответ `201 Created` — объект `User` (см. раздел 4), плюс тот же заголовок `Set-Cookie`, что и при входе.

Если аккаунт создан, а сессию выдать не удалось, ответ всё равно `201`, но без cookie: регистрация
состоялась, и отвечать ошибкой нельзя — на повторную попытку пользователь получил бы `409 email_taken`.
Фронт в этом случае увидит `401` на `GET /me` и покажет форму входа.

Ошибки:

| Код | `error.code` | Когда |
|---|---|---|
| 400 | `invalid_json` | тело не разобралось |
| 400 | `validation_failed` | поля не прошли проверку, в `fields` детали |
| 409 | `email_taken` | email уже зарегистрирован |
| 500 | `internal_error` | сбой хранилища |

Пример ошибки занятого email:

```json
{ "error": { "code": "email_taken", "message": "Пользователь с таким email уже существует" } }
```

Замечание для реализации: два одновременных запроса с одинаковым email не должны создать два аккаунта.
Проверка «есть ли такой email» перед вставкой не спасает — полагаемся на уникальный индекс в БД
и превращаем его нарушение в `409`.

### 6.2 `POST /api/v1/auth/login` — вход

Запрос:

```json
{ "email": "andrey@example.com", "password": "muzyka2026" }
```

Ответ `200 OK` — объект `User`, плюс заголовок:

```
Set-Cookie: session_id=<...>; Path=/; HttpOnly; SameSite=Lax; Max-Age=86400
```

Ошибки:

| Код | `error.code` | Когда |
|---|---|---|
| 400 | `invalid_json` | тело не разобралось |
| 400 | `validation_failed` | пустой email или пароль |
| 401 | `invalid_credentials` | неизвестный email **или** неверный пароль |
| 500 | `internal_error` | сбой хранилища |

Ответ при неизвестном email и при неверном пароле **одинаковый** — иначе по разнице ответов
перебирают существующие аккаунты:

```json
{ "error": { "code": "invalid_credentials", "message": "Неверный email или пароль" } }
```

### 6.3 `GET /api/v1/auth/me` — текущий пользователь

Запрос без тела, cookie приходит автоматически. Фронт вызывает эту ручку при старте приложения,
чтобы восстановить сессию после перезагрузки страницы.

Ответ `200 OK` — объект `User`.

Ошибки:

| Код | `error.code` | Когда |
|---|---|---|
| 401 | `unauthorized` | нет cookie, сессия неизвестна, истекла или пользователь удалён |
| 500 | `internal_error` | сбой хранилища |

401 — это **нормальный** ответ для гостя, а не аварийная ситуация. Фронт показывает гостевой интерфейс
и никаких сообщений об ошибке.

### 6.4 `POST /api/v1/auth/logout` — выход

Запрос без тела.

Ответ `204 No Content` с заголовком, гасящим cookie:

```
Set-Cookie: session_id=; Path=/; HttpOnly; Max-Age=0
```

- Повторный выход, выход без cookie и выход с истёкшей сессией тоже дают **204**: результат тот же,
  пользователь не авторизован.
- `500 internal_error` — только если хранилище не смогло удалить сессию.

### 6.5 `GET /api/v1/home` — данные главной страницы

Публичная ручка: работает и для гостя, и для вошедшего пользователя, ответ одинаковый.

Ответ `200 OK`:

```json
{
  "tracks": [
    {
      "id": "1001",
      "title": "Летний дождь",
      "duration_ms": 214000,
      "cover_url": "https://cdn.example.com/covers/1001.jpg",
      "artists": [ { "id": "7", "name": "Кино" } ]
    }
  ],
  "artists": [
    { "id": "7", "name": "Кино", "image_url": "https://cdn.example.com/artists/7.jpg" }
  ],
  "albums": [
    {
      "id": "300",
      "title": "Группа крови",
      "release_date": "1988-08-01",
      "cover_url": "https://cdn.example.com/albums/300.jpg",
      "artists": [ { "id": "7", "name": "Кино" } ]
    }
  ]
}
```

- В каждом разделе **не более 20** объектов.
- Порядок: сначала новые (по `created_at` убыванию). Это временное правило РК1;
  подборки и чарты появятся позже.
- В `tracks` попадают только опубликованные треки (`track.status`); допустимые значения статуса
  уточняются у Фёдора.
- Пустой раздел — это `[]`, **никогда не `null`**. Фронт в этом случае рисует пустое состояние.
- Ошибка чтения каталога — `500 internal_error`; сервер при этом не падает.

Пример пустого каталога:

```json
{ "tracks": [], "artists": [], "albums": [] }
```

### 6.6 `GET /health` — проверка живости

Живёт **вне** `/api/v1`, используется мониторингом и при деплое.
Ответ `200 OK`, тело `{"status":"ok"}`.

## 7. Сценарий, который показываем на РК1

1. `POST /api/v1/auth/signup` → 201, аккаунт в PostgreSQL и cookie сессии.
2. `POST /api/v1/auth/logout`, затем `POST /api/v1/auth/login` → 200 и новая cookie.
3. `GET /api/v1/auth/me` → 200, тот же пользователь (в том числе после перезагрузки страницы).
4. `GET /api/v1/home` → 200, три непустых массива.
5. `POST /api/v1/auth/logout` → 204.
6. `GET /api/v1/auth/me` → 401, интерфейс снова гостевой.

Проверка руками:

```
curl -i -c cookies.txt -X POST http://localhost:8080/api/v1/auth/signup \
  -H 'Content-Type: application/json' \
  -d '{"email":"andrey@example.com","password":"muzyka2026","display_name":"Андрей"}'

curl -i -c cookies.txt -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"andrey@example.com","password":"muzyka2026"}'

curl -i -b cookies.txt http://localhost:8080/api/v1/auth/me
curl -i http://localhost:8080/api/v1/home
curl -i -b cookies.txt -X POST http://localhost:8080/api/v1/auth/logout
```

## 8. Связь с БД (зона Фёдора)

Контракт опирается на схему из ветки `MUSIC-4` (`db/normalized/er.md`, `db/normalized/relations.md`).

| Поле API | Источник в схеме |
|---|---|
| `user.id` | `account.id` |
| `user.email` | `account.email` (уникальный) |
| `user.display_name` | `account.display_name` |
| `user.avatar_url` | `account.avatar_file_id` → `media_file` |
| `track.duration_ms` | `media_file.duration_ms` через `track.audio_file_id` |
| `track.cover_url` | `track.cover_file_id` → `media_file(bucket, object_key)` |
| `track.artists` | `track_artist` → `artist` |
| `album.artists` | `album_artist` → `artist` |

Хранение пароля: одна колонка `account.password_hash` типа `text`. Хешируем **bcrypt**
(`golang.org/x/crypto/bcrypt`, согласован с Тимофеем 25.09). Формат строки —
`$2a$<цена>$<соль и хеш>`, 60 символов; соль bcrypt генерирует сам и хранит внутри строки,
отдельная колонка под неё не нужна. Цена записана в самом хеше, поэтому сиды с ценой 12
проверяются тем же кодом, что и новые пароли.
