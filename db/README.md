# База данных

В проекте используется PostgreSQL и драйвер `pgx/v5`. ORM не используется: запросы написаны вручную, SQL-миграции хранятся в [`migrations/`](migrations/). Сервер подключается к БД через пул `pgxpool` по `POSTGRES_DSN` и проверяет соединение при запуске.

Документация полной модели, функциональных зависимостей и ограничений: [`normalized/relations.md`](normalized/relations.md). Диаграмма: [`normalized/er.md`](normalized/er.md).

## ДЗ 3. Учебный стенд

Docker Compose запускает один Go API (`server`) и одну PostgreSQL 18 (`db`). При подготовке базы `db-roles` настраивает роли, `migrate` применяет миграции, `db-grants` выдаёт права. Для проверок к базе подключаются `db-monitor` и `db-check`.

| Операция | Целевой p95 |
|---|---:|
| `GET /api/v1/home` | 400 мс |
| `POST /api/v1/auth/login` | 800 мс |
| `PUT /api/v1/users/{id}` без файла | 500 мс |

### Лимиты соединений

Для стенда закладываем 8 соединений для пула API, 4 для мигратора, 3 для мониторинга, 2 для проверок и 5 на администрирование и запас. Всего 22 из 97 доступных обычных соединений. Лимит PostgreSQL — 100, три из них зарезервированы для суперпользователей. На API и проверки приходится 10 из 30 соединений, разрешённых роли `music_api`.

### Таймауты и журнал PostgreSQL

Под ролью `music_api` команда `SHOW` вернула `statement_timeout = 5s`, `lock_timeout = 2s` и `idle_in_transaction_session_timeout = 15s`. При проверках PostgreSQL прервал долгий запрос с кодом `57014`, а ожидание блокировки — с кодом `55P03`. [Скрипт проверки значений](checks/settings.sql)

Коллектор пишет CSV в `$PGDATA/log`. Запросы от 500 мс записываются в журнал, чтобы видеть медленные операции. Ротация через 1 час или при достижении 20 МиБ ограничивает время и размер одного файла. Запись значений параметров SQL отключена. [Настройки коллектора](admin/diagnostics.conf)

В примерах из тестового CSV показаны время, уровень, код и сообщение.

```csv
2026-11-25 08:07:09.875 UTC,LOG,00000,duration: 661.211 ms  statement: SELECT pg_sleep(0.65) AS dz3_slow_check;
2026-11-25 08:07:09.877 UTC,ERROR,22012,division by zero
```

### Статистика запросов и план

PostgreSQL читает `diagnostics.conf` через `include` и загружает `pg_stat_statements` при старте. `db-roles` создаёт расширение в базе `music`. После трёх запросов к главной в статистике у запроса треков `WITH selected_tracks AS (...)` было `calls = 3`. [Подключение конфига](admin/postgresql.conf) · [Запрос статистики](monitoring/catalog-statements.sql)

Команды выполняются из корня проекта в Bash.

```bash
export DOCKER_HTTP_PORT=18080 DOCKER_POSTGRES_PORT=15433
project=music-dz3-check
base=http://127.0.0.1:18080
docker compose -p "$project" up --build --wait
docker compose -p "$project" run --rm --no-deps -T db-monitor -f /monitoring/catalog-statements.sql
for i in 1 2 3; do curl -fsS "$base/api/v1/home" >/dev/null; done
docker compose -p "$project" run --rm --no-deps -T db-monitor -f /monitoring/catalog-statements.sql
docker compose -p "$project" run --rm --no-deps -T -e PGAPPNAME=music-diagnostics db-roles -f /checks/diagnostics.sql
```

Последняя команда включает `auto_explain` в проверочной сессии с порогом 500 мс. PostgreSQL автоматически записал этот план в CSV. [Сценарий диагностики](checks/diagnostics.sql)

```text
duration: 650.929 ms  plan:
Query Text: SELECT pg_sleep(0.65) AS dz3_slow_check;
Result  (cost=0.00..0.01 rows=1 width=4)
```

### Отчёт pgBadger

После проверки копируем CSV тестового стенда и собираем `db/diagnostics-output/report.html`. В готовом отчёте видны медленный запрос и ошибка `division by zero`. HTML прикладывается к PR отдельно.

```bash
out="$PWD/db/diagnostics-output"
mkdir -p "$out"
logs=$(mktemp -d)
db_id=$(docker compose -p "$project" ps -q db)
pgdata=$(docker compose -p "$project" exec -T db printenv PGDATA)
docker cp "$db_id:$pgdata/log/." "$logs"
docker build -t navse200-pgbadger:local db/monitoring
docker run --rm --network none -v "$logs:/logs:ro" -v "$out:/out" \
  --entrypoint sh navse200-pgbadger:local -c 'pgbadger -f csv -o /out/report.html /logs/*.csv'
```

## Схема данных

Схема нормализована и описывает музыкальный сервис:

- account, auth_session — аккаунты и серверные сессии;
- media_file — метаданные медиафайлов;
- artist, album, track и таблицы связей track_artist, album_artist, album_track — музыкальный каталог;
- playlist, playlist_item, favorite_track — плейлисты и избранное;
- chart, chart_item, listening_event — чарты и события прослушивания.

В качестве идентификаторов используются uuid; для временных меток — timestamptz, для даты релиза — date. Ограничения PRIMARY KEY, FOREIGN KEY, UNIQUE и CHECK задают целостность данных: например, уникальность email, допустимые статусы трека, положительные номера позиций и согласованные временные интервалы. Связи используют явно заданные правила ON DELETE и ON UPDATE. Состав и точные условия ограничений приведены в документации модели.

Дополнительные индексы для ускорения запросов и денормализация не добавлялись. Индексы, создаваемые ограничениями PRIMARY KEY и UNIQUE, используются для обеспечения целостности.

## Миграции

Миграции — чистый SQL, для каждой предусмотрены файлы .up.sql и .down.sql:

| Версия | Назначение |
|---|---|
| `000001_create_schema` | Создание таблиц музыкального сервиса, ключей, проверок и триггеров `updated_at`. |
| `000002_seed_account` | Создание служебного аккаунта каталога. Треки и медиафайлы не создаются. |
| `000003_enforce_media_roles` | Проверка, что аудиофайлы используются для аудио, а изображения — для аватаров и обложек. Категорию существующего файла менять нельзя. |
| `000004_create_auth_session` | Создание таблицы серверных сессий с внешним ключом на аккаунт и проверками временных меток. |
| `000005_media_local_storage` | Замена `bucket` и `object_key` на единый относительный `storage_key`. |

Команда app migrate применяет миграции через golang-migrate с драйвером pgx/v5. SQL-файлы встраиваются из [migrations/](migrations/). Состояние версий хранится в schema_migrations. Миграции автоматически запускает сервис migrate в Docker Compose; сервер сам схему не меняет.

Применённые миграции не редактируйте — изменения схемы оформляйте новой парой файлов. Перед откатом проверьте соответствующий .down.sql: он может удалять таблицы или данные. Миграция 000005 изменяет только метаданные БД, не перемещает файлы. Откат этой миграции невозможен для некоторых новых storage_key (например, без /) и в таких случаях атомарно завершится ошибкой.

Для новой установки используйте пустую базу. Если таблицы были созданы вручную, не запускайте миграции поверх них и не устанавливайте baseline без сверки фактической схемы, ограничений, триггеров и данных.

## Использование в backend

В [internal/repository/postgres/](../internal/repository/postgres/) находятся:

- user_repo.go — создание пользователя и поиск по ID или email;
- session_repo.go — сохранение, чтение, удаление сессии и очистка истёкших сессий;
- catalog_repo.go — чтение треков, исполнителей и альбомов для главной страницы.
- profile_repo.go — методы UserRepo для изменения имени и привязки аватара;
- account_repo.go — смена email, смена пароля с отзывом сессий и удаление аккаунта в транзакциях;
- media_repo.go — сохранение и чтение метаданных файлов;
- artist_repo.go — данные исполнителя, его опубликованные треки и альбомы;
- track_repo.go — опубликованный трек с исполнителями и метаданные его аудио.

Исполнитель подключён через usecase и GET /api/v1/artists/{id}: данные, опубликованные треки и альбомы с пагинацией. Профиль и плеер пока подготовлены на уровне репозиториев; HTTP-маршруты для них ещё не подключены.

Запросы написаны явно, параметры передаются через $1, $2 и далее. Репозитории возвращают модели и ошибки, а HTTP-ответы формируют обработчики. Пустой каталог допустим: API возвращает пустые списки.

Регистрация сохраняет аккаунт и сессию отдельными операциями. Если создание сессии не удалось, уже созданный аккаунт остаётся в БД. Редактирование музыкального каталога, плейлисты, избранное, история и чарты пока не реализованы в репозиториях. Таблицы для этих функций остаются в схеме БД.

## Медиафайлы

В БД хранится уникальный media_file.storage_key — относительный путь внутри предполагаемого общего корня хранения, например audio/track.mp3. Ключ не содержит абсолютный путь сервера или публичный URL. Ограничение не допускает пустой ключ, начальный или конечный /, пустые компоненты, . и .., обратную косую черту, :, управляющие символы.

MediaRepo сохраняет метаданные в media_file, но API загрузки и файловый слой пока не реализованы. Настройка MEDIA_ROOT, volume для медиа, загрузка и скачивание байтов будут добавлены вместе с этой функцией. Миграция 000005 меняет только метаданные БД и не переносит файлы. URL изображений в каталоге пока не формируются.

Будущий обработчик аватара принимает multipart/form-data. Сценарий проверяет изображение и сохраняет байты в файловый слой, затем записывает метаданные через MediaRepo.Create и привязывает файл через UserRepo.SetAvatar. При ошибке нужно предусмотреть очистку созданных файлов и метаданных: две операции БД пока отдельные. Репозитории не принимают HTTP-запросы и multipart.FileHeader.

TrackRepo.GetAudio возвращает storage_key, MIME-тип, размер и длительность. Выдача аудио и поддержка HTTP Range для перемотки выполняются в HTTP-слое. Пауза, громкость и переходы по очереди треков выполняются на клиенте.

## Запуск

### Вся система в Docker Compose

Из корня репозитория:

```powershell
docker compose up --build -d
docker compose ps -a
docker compose logs migrate
```

Compose запускает PostgreSQL, затем миграции и сервер. Успешно завершившийся контейнер migrate со статусом Exited (0) — нормальный результат. Сервер не стартует, если миграции завершились ошибкой. API доступно на http://localhost:8080; порт API и порт PostgreSQL можно изменить через DOCKER_HTTP_PORT и DOCKER_POSTGRES_PORT. Для локальной разработки используется пароль DOCKER_POSTGRES_PASSWORD (по умолчанию music_local_dev).

### Команды миграций в Docker

При запуске всей системы миграции выполняются автоматически перед сервером. Чтобы отдельно применить миграции или посмотреть версию, выполните из корня проекта:

```powershell
docker compose run --rm migrate up
docker compose run --rm migrate version
```

Для отката заданного числа миграций команда принимает down и положительное число шагов. Перед откатом проверьте соответствующие SQL-файлы: они могут удалять таблицы и данные.

```powershell
docker compose run --rm migrate down 1
```

Сервис migrate получает подключение к БД из compose.yaml.

### Устройство мигратора

cmd/app/main.go обрабатывает сигналы остановки. Команда migrate вызывает internal/migration.Run, команда server — internal/app.Run. В пакете internal/migration обязанности разделены:

- command.go — проверка аргументов up, down и version;
- database.go — подключение к PostgreSQL и таймауты;
- migration.go — создание мигратора, выполнение команды и вывод версии;
- transaction.go — выполнение одного SQL-файла в транзакции;
- run.go — последовательность вызовов и закрытие ресурсов.

Каждый файл выполняется в отдельной транзакции Go. Внешние BEGIN/COMMIT из существующих файлов снимаются только в памяти перед выполнением. SQL-файлы и история миграций не меняются. При ошибке или отмене выполняется откат текущего файла; предыдущие успешно применённые версии остаются в БД. Таймаут одной миграции — одна минута, ожидания блокировки БД — 15 секунд. Ctrl+C и SIGTERM отменяют контекст выполнения.

Версии и блокировку между процессами по-прежнему ведёт golang-migrate. После ошибки миграция остаётся помеченной dirty, даже если её изменения отменены. Повторный запуск не сбрасывает этот признак автоматически: сначала нужно проверить состояние БД и устранить причину сбоя.

### Изменение и удаление аккаунта

Все операции требуют cookie session_id и UUID собственного аккаунта. Чужой ID — 403, отсутствующая/закрытая сессия — 401. JSON ограничен 16 КиБ; неизвестные поля и второй JSON-объект отклоняются с 400 invalid_json.

| Метод и путь | JSON | Успех |
|---|---|---|
| `PUT /api/v1/users/{id}/email` | `{"email":"new@example.com","current_password":"..."}` | 200, обновлённый профиль |
| `PUT /api/v1/users/{id}/password` | `{"current_password":"...","new_password":"..."}` | 204, все сессии закрыты, cookie удалена |
| `DELETE /api/v1/users/{id}` | `{"current_password":"..."}` | 204, аккаунт удалён, cookie удалена |

Email нормализуется. Занятый адрес — 409 email_taken. Неверный текущий пароль — 400 invalid_current_password с fields.current_password. Неверные поля — 400 validation_failed; новый пароль проверяется по тем же правилам, что при регистрации: от 8 символов, не более 72 байт, хотя бы одна буква и цифра. Ошибка нового пароля возвращается в fields.new_password. Пароль хранится только в виде bcrypt-хеша.

Удаление закрывает все сессии, удаляет плейлисты, избранное и историю пользователя. Загруженные треки общего каталога передаются служебному аккаунту каталога. Служебный аккаунт удалить нельзя. Файлы медиа и их метаданные автоматически не удаляются. Смена пароля и отзыв сессий, а также удаление аккаунта и зависимых данных выполняются в транзакциях. Перед записью под блокировкой проверяется актуальность хеша пароля.

Во фронтенде /profile доступны «Сменить email», «Сменить пароль» и «Удалить аккаунт». Удаление подтверждается отдельной формой с текущим паролем; при смене пароля есть поле повторного ввода. После смены email профиль обновляется; после смены пароля или удаления очищаются пользовательское состояние и оффлайн-кэш, открывается вход.
