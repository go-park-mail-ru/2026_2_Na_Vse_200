## Что подключено

- Аккаунты: `internal/repository/postgres/user_repo.go` — создание, поиск по ID и email.
- Главная страница: `internal/repository/postgres/catalog_repo.go` — опубликованные треки, исполнители и альбомы. Связи с исполнителями читаются вместе с выбранными записями, без запроса для каждого элемента.
- Подключение: `cmd/server/main.go`, пул `pgxpool`, настройка `POSTGRES_DSN`, проверка соединения при старте.
- Сессии сейчас хранятся в памяти процесса. Redis указан в проектной модели как следующее хранилище, его реализация ещё не подключена. Перезапуск сервера завершает текущие сессии, но аккаунты остаются в PostgreSQL.
- S3 и выдача адресов медиафайлов ещё не подключены. Поля `ImageURL`/`CoverURL` в PostgreSQL-каталоге пока пустые; фиктивных адресов нет.

Пустой музыкальный каталог допустим: API возвращает пустые массивы. Наполнение музыкой не требуется для создания схемы и не выполняется при старте сервера.

## Запуск через Docker Compose

Для локального запуска нужны Docker Engine с Compose или Docker Desktop в режиме Linux containers. Go и PostgreSQL на компьютере для этого способа не требуются. Из корня проекта:

```powershell
docker compose up --build -d
docker compose ps -a
docker compose logs migrate
```

Compose создаёт отдельную базу `music`, ждёт готовности PostgreSQL, запускает SQL-миграции и затем Go-сервер. Завершённый `migrate` со статусом `Exited (0)` — нормальный результат. При ошибке миграций сервер не запускается; причину смотрите в `docker compose logs migrate`.

Проверка API: [http://localhost:8080/health](http://localhost:8080/health) и [http://localhost:8080/api/v1/home](http://localhost:8080/api/v1/home). Логи сервера:

```powershell
docker compose logs -f server
```

Первый запуск работает без `.env`. Уже существующий `.env` сохраняйте: Compose берёт только явно перечисленные настройки, токены музыкальных сервисов ему не нужны. Внутри контейнеров `POSTGRES_DSN` указывает на `db:5432`, а пароль передаётся отдельно через `PGPASSWORD`. Локальный `POSTGRES_DSN` из `.env` не используется контейнерами.

| Настройка Compose | По умолчанию | Назначение |
|---|---|---|
| `DOCKER_HTTP_PORT` | `8080` | порт API на компьютере |
| `DOCKER_POSTGRES_PORT` | `5433` | порт PostgreSQL на компьютере |
| `DOCKER_POSTGRES_PASSWORD` | `music_local_dev` | пароль пользователя `music` для локальной разработки |

При необходимости добавьте эти переменные в существующий `.env`. Для подключения SQLTools укажите `localhost`, порт `5433`, базу `music`, пользователя `music`, пароль `music_local_dev` либо своё значение `DOCKER_POSTGRES_PASSWORD`, SSL отключён. Если `8080` занят локально запущенным Go-сервером, остановите его или задайте другой `DOCKER_HTTP_PORT`.

База контейнера независима от установленного PostgreSQL на `localhost:5432`: существующие таблицы и данные автоматически не переносятся. Docker хранит файлы новой базы в именованном volume `navse200_postgres_data`, подключённом к `/var/lib/postgresql`. Этот путь соответствует официальному образу PostgreSQL 18. Обычная остановка сохраняет данные:

```powershell
docker compose down
```

Удаление самого volume удалит базу. `DOCKER_POSTGRES_PASSWORD` применяется при первоначальном создании базы; изменение переменной в `.env` не меняет пароль уже существующего пользователя PostgreSQL. Для удалённого развёртывания задайте отдельный пароль и настройки сети/TLS своего сервера.

После изменения Go-кода или добавления миграции запускайте:

```powershell
docker compose up --build -d
```

`docker compose restart` перезапускает старые контейнеры и не пересобирает код и не применяет новые миграции. Отдельно проверить версию схемы и открыть SQL-консоль можно так:

```powershell
docker compose run --rm migrate version
docker compose exec db psql -U music -d music
```

Для отката остановите API и проверьте соответствующий `.down.sql`:

```powershell
docker compose stop server
docker compose run --rm migrate down 1
```

Повторный полный `docker compose up --build -d` снова применит доступные `.up.sql`. Для работы на более старой схеме нужен совместимый с ней код. Ограничения отката служебного аккаунта описаны ниже.

Описание порядка запуска: [Docker Compose](https://docs.docker.com/compose/how-tos/startup-order/). Особенности хранения PostgreSQL 18: [официальный образ PostgreSQL](https://hub.docker.com/_/postgres).

## Развёртывание новой базы без Docker

Нужен PostgreSQL с кодировкой UTF8. Подключитесь к служебной базе `postgres` через psql или SQLTools и создайте отдельную пустую базу разработки:

```sql
CREATE DATABASE music_hw2;
```

В корне проекта настройте локальную `.env` по `.env.example`. Если `.env` уже существует, добавьте в него `POSTGRES_DSN`, сохранив остальные настройки. Файл `.env` исключён из Git.

```dotenv
POSTGRES_DSN=postgres://postgres:YOUR_PASSWORD@localhost:5432/music_hw2?sslmode=disable
```

`sslmode=disable` в примере предназначен для локального соединения. Для удалённой базы используйте настройки TLS своего сервера. Зарезервированные символы пароля в URI необходимо URL-кодировать.

В PowerShell из корня проекта:

```powershell
.\scripts\run.ps1 go run ./cmd/migrate up
.\scripts\run.ps1 go run ./cmd/migrate version
.\scripts\run.ps1
```

В Bash/Git Bash используются те же команды через `./scripts/run.sh`:

```bash
./scripts/run.sh go run ./cmd/migrate up
./scripts/run.sh go run ./cmd/migrate version
./scripts/run.sh
```

Команда миграций использует `golang-migrate` и драйвер `pgx/v5`. SQL-файлы встраиваются в неё из `db/migrations`, DDL остаётся чистым SQL. Docker Compose запускает эту же команду отдельным сервисом `migrate`. `schema_migrations` хранит номер применённой миграции и признак незавершённого применения. Сервер сам миграции не запускает.

## Уже созданная вручную база

Если таблицы базы `music` ранее создавались из SQLTools, наличие таблиц не означает, что у инструмента миграций есть история их создания. При отсутствии `schema_migrations` не запускайте `up` или принудительную установку версии вслепую: повторное создание таблиц завершится ошибкой, а неверный baseline скроет различия схемы.

Для ДЗ безопаснее использовать новую пустую `music_hw2`, как в инструкции выше. Базу `music` и её данные можно сохранить. Перенос существующей базы под управление миграций требует отдельно сверить все таблицы, ограничения, функции, триггеры и начальные данные с версиями SQL; только после такой сверки согласуют baseline.

## Миграции и откат

- `000001_create_schema` создаёт нормализованные таблицы, ключи, проверки и триггеры `updated_at`.
- `000002_seed_account` создаёт служебный аккаунт, на который могут ссылаться загруженные треки; музыкальных файлов и треков он не добавляет.
- `000003_enforce_media_roles` проверяет, что аудиоссылки ведут на аудио, а аватары и обложки — на изображения. Смена категории существующего `media_file` между аудио и изображением запрещена: для замены создайте новую запись файла. Некорректные существующие связи должны быть исправлены перед применением миграции.

Откат последней миграции:

```powershell
.\scripts\run.ps1 go run ./cmd/migrate down 1
```

Для `down` необходимо явно указать положительное число шагов. Откат может удалить таблицы или данные соответствующих миграций; перед ним проверьте содержимое `.down.sql`. Удаление служебного аккаунта миграцией `000002` будет отклонено внешним ключом, если на него уже ссылаются треки. Автоматически удалять настоящие треки ради отката нельзя.

Применённые SQL-файлы не редактируют: дальнейшее изменение схемы оформляется новой парой `.up.sql`/`.down.sql`. Если миграция завершилась ошибкой, сначала исправьте её причину и проверьте фактическую схему; сброс dirty-флага сам по себе не исправляет базу.

## Транзакции и конкурентные изменения

Сейчас единственная прикладная SQL-запись — создание аккаунта одним `INSERT ... RETURNING`. Один SQL-оператор атомарен: дополнительный `BEGIN` вокруг него не создаст новых гарантий. Уникальность email обеспечивает ограничение БД, поэтому предварительная проверка существования email не заменяет обработку конфликта вставки.

Каждый метод каталога выполняет один `SELECT`: треки/альбомы сначала ограничиваются по количеству, затем одним запросом присоединяются исполнители. `LIMIT` не обрезает исполнителей одного элемента. Используется стандартная изоляция PostgreSQL `READ COMMITTED`. Три части ответа главной читаются отдельно; общий неизменный снимок всего ответа API сейчас не обещает.

Регистрация сохраняет аккаунт в PostgreSQL, затем создаёт сессию в другом хранилище. Если создание сессии не удалось, аккаунт остаётся сохранённым; пользователь может выполнить обычный вход. Единой транзакции PostgreSQL и памяти/будущего Redis нет.

При реализации загрузки трека записи `media_file`, `track` и его связей должны создаваться одной SQL-транзакцией. Загрузка объекта S3 находится вне неё; неиспользованные объекты удаляют отдельной очисткой. Для изменения состава плейлиста нужны транзакция, пакетная запись элементов и проверка ожидаемого `playlist.revision` с увеличением версии. Эти операции и методы ещё не реализованы; само наличие поля `revision` не означает, что оптимистическая блокировка уже работает. Уровень изоляции и обработку конфликтов выбирают вместе с конкретной операцией.

## Соответствие требованиям ДЗ

| Требование | Где посмотреть |
|---|---|
| Драйвер pgx | `go.mod`, `cmd/server/main.go`, `internal/repository/postgres/`, `cmd/migrate/` |
| Без ORM, SQL написан вручную | `internal/repository/postgres/user_repo.go`, `catalog_repo.go` |
| Миграции на чистом SQL | `db/migrations/*.sql`, запуск через `cmd/migrate` |
| Постоянные запросы в строковых константах | SQL-константы PostgreSQL-репозиториев |
| Рекомендации PostgreSQL | `text`, `uuid`, `timestamptz`, нижний регистр имён; без `serial`, `money`, `char(n)`, rules и наследования таблиц. Список: [Don't Do This](https://wiki.postgresql.org/wiki/Don't_Do_This) |
| Согласованные операции и пакетная работа | Раздел о транзакциях выше, ограничения миграций, запросы каталога без N+1 |
| Без преждевременных индексов и денормализации | Нормализованная модель; индексы от `PRIMARY KEY`/`UNIQUE` обеспечивают ограничения, отдельные индексы ради ускорения не добавлены |

Код и инструкции готовятся в отдельной ветке командного репозитория. Доступы проверяющим, обсуждение в issues и аппрувы ментора и преподавателя оформляются отдельно; локальная проверка кода не заменяет сдачу. Дедлайн из задания — 28 октября 2026 включительно.
