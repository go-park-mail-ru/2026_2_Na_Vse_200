# База данных

В проекте используется PostgreSQL и драйвер `pgx/v5`. ORM не используется: запросы написаны вручную, SQL-миграции хранятся в [`migrations/`](migrations/). Сервер подключается к БД через пул `pgxpool` по `POSTGRES_DSN` и проверяет соединение при запуске.

Документация полной модели, функциональных зависимостей и ограничений: [`normalized/relations.md`](normalized/relations.md). Диаграмма: [`normalized/er.md`](normalized/er.md).

## Схема данных

Схема нормализована и описывает музыкальный сервис:

- `account`, `auth_session` — аккаунты и серверные сессии;
- `media_file` — метаданные медиафайлов;
- `artist`, `album`, `track` и таблицы связей `track_artist`, `album_artist`, `album_track` — музыкальный каталог;
- `playlist`, `playlist_item`, `favorite_track` — плейлисты и избранное;
- `chart`, `chart_item`, `listening_event` — чарты и события прослушивания.

В качестве идентификаторов используются `uuid`; для временных меток — `timestamptz`, для даты релиза — `date`. Ограничения `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE` и `CHECK` задают целостность данных: например, уникальность email, допустимые статусы трека, положительные номера позиций и согласованные временные интервалы. Связи используют явно заданные правила `ON DELETE` и `ON UPDATE`. Состав и точные условия ограничений приведены в документации модели.

Дополнительные индексы для ускорения запросов и денормализация не добавлялись. Индексы, создаваемые ограничениями `PRIMARY KEY` и `UNIQUE`, используются для обеспечения целостности.

## Миграции

Миграции — чистый SQL, для каждой предусмотрены файлы `.up.sql` и `.down.sql`:

| Версия | Назначение |
|---|---|
| `000001_create_schema` | Создание таблиц музыкального сервиса, ключей, проверок и триггеров `updated_at`. |
| `000002_seed_account` | Создание служебного аккаунта каталога; треки и медиафайлы не создаются. |
| `000003_enforce_media_roles` | Проверка, что аудиофайлы используются для аудио, а изображения — для аватаров и обложек. Категорию существующего файла менять нельзя. |
| `000004_create_auth_session` | Создание таблицы серверных сессий с внешним ключом на аккаунт и проверками временных меток. |
| `000005_media_local_storage` | Замена `bucket` и `object_key` на единый относительный `storage_key`. |

Команда `app migrate` применяет миграции через `golang-migrate` с драйвером `pgx/v5`. SQL-файлы встраиваются из [`migrations/`](migrations/). Состояние версий хранится в `schema_migrations`. Миграции автоматически запускает сервис `migrate` в Docker Compose; сервер сам схему не меняет.

Применённые миграции не редактируйте — изменения схемы оформляйте новой парой файлов. Перед откатом проверьте соответствующий `.down.sql`: он может удалять таблицы или данные. Миграция `000005` изменяет только метаданные БД, не перемещает файлы. Откат этой миграции невозможен для некоторых новых `storage_key` (например, без `/`) и в таких случаях атомарно завершится ошибкой.

Для новой установки используйте пустую базу. Если таблицы были созданы вручную, не запускайте миграции поверх них и не устанавливайте baseline без сверки фактической схемы, ограничений, триггеров и данных.

## Использование в backend

В [internal/repository/postgres/](../internal/repository/postgres/) находятся:

- user_repo.go — создание пользователя и поиск по ID или email;
- session_repo.go — сохранение, чтение, удаление сессии и очистка истёкших сессий;
- catalog_repo.go — чтение треков, исполнителей и альбомов для главной страницы.
- profile_repo.go — методы UserRepo для изменения email, имени и привязки аватара;
- media_repo.go — сохранение и чтение метаданных файлов;
- artist_repo.go — данные исполнителя, его опубликованные треки и альбомы;
- track_repo.go — опубликованный трек с исполнителями и метаданные его аудио.

Профиль, исполнитель и плеер пока подготовлены на уровне репозиториев.
Новые HTTP-маршруты и usecase для них ещё не подключены.

Запросы написаны явно, параметры передаются через $1, $2 и далее.
Репозитории возвращают модели и ошибки, а HTTP-ответы формируют обработчики.
Пустой каталог допустим: API возвращает пустые списки.

Регистрация сохраняет аккаунт и сессию отдельными операциями. Если создание
сессии не удалось, уже созданный аккаунт остаётся в БД.
Редактирование музыкального каталога, плейлисты, избранное, история и чарты
пока не реализованы в репозиториях.
Таблицы для этих функций остаются в схеме БД.

## Медиафайлы

В БД хранится уникальный `media_file.storage_key` — относительный путь внутри предполагаемого общего корня хранения, например `audio/track.mp3`. Ключ не содержит абсолютный путь сервера или публичный URL. Ограничение не допускает пустой ключ, начальный или конечный `/`, пустые компоненты, `.` и `..`, обратную косую черту, `:`, управляющие символы.

MediaRepo сохраняет метаданные в media_file, но API загрузки и файловый слой
пока не реализованы. Настройка MEDIA_ROOT, volume для медиа, загрузка и скачивание
байтов будут добавлены вместе с этой функцией. Миграция 000005 меняет только
метаданные БД и не переносит файлы. URL изображений в каталоге пока не формируются.

Будущий обработчик аватара принимает multipart/form-data. Сценарий проверяет
изображение и сохраняет байты в файловый слой, затем записывает метаданные через
MediaRepo.Create и привязывает файл через UserRepo.SetAvatar. При ошибке нужно
предусмотреть очистку созданных файлов и метаданных: две операции БД пока отдельные.
Репозитории не принимают HTTP-запросы и multipart.FileHeader.

TrackRepo.GetAudio возвращает storage_key, MIME-тип, размер и длительность.
Выдача аудио и поддержка HTTP Range для перемотки выполняются в HTTP-слое.
Пауза, громкость и переходы по очереди треков выполняются на клиенте.

## Запуск

### Вся система в Docker Compose

Из корня репозитория:

```powershell
docker compose up --build -d
docker compose ps -a
docker compose logs migrate
```

Compose запускает PostgreSQL, затем миграции и сервер. Успешно завершившийся контейнер `migrate` со статусом `Exited (0)` — нормальный результат. Сервер не стартует, если миграции завершились ошибкой. API доступно на `http://localhost:8080`; порт API и порт PostgreSQL можно изменить через `DOCKER_HTTP_PORT` и `DOCKER_POSTGRES_PORT`. Для локальной разработки используется пароль `DOCKER_POSTGRES_PASSWORD` (по умолчанию `music_local_dev`).

### Команды миграций в Docker

При запуске всей системы миграции выполняются автоматически перед сервером.
Чтобы отдельно применить миграции или посмотреть версию, выполните из корня проекта:

```powershell
docker compose run --rm migrate up
docker compose run --rm migrate version
```

Для отката заданного числа миграций команда принимает down и положительное
число шагов. Перед откатом проверьте соответствующие SQL-файлы: они могут
удалять таблицы и данные.

```powershell
docker compose run --rm migrate down 1
```

Сервис migrate получает подключение к БД из compose.yaml.

### Устройство мигратора

cmd/app/main.go обрабатывает сигналы остановки. Команда migrate вызывает internal/migration.Run, команда server — internal/app.Run.
В пакете internal/migration обязанности разделены:

- command.go — проверка аргументов up, down и version;
- database.go — подключение к PostgreSQL и таймауты;
- migration.go — создание мигратора, выполнение команды и вывод версии;
- transaction.go — выполнение одного SQL-файла в транзакции;
- run.go — последовательность вызовов и закрытие ресурсов.

Каждый файл выполняется в отдельной транзакции Go. Внешние BEGIN/COMMIT из
существующих файлов снимаются только в памяти перед выполнением. SQL-файлы
и история миграций не меняются. При ошибке или отмене выполняется откат
текущего файла; предыдущие успешно применённые версии остаются в БД.
Таймаут одной миграции — одна минута, ожидания блокировки БД — 15 секунд.
Ctrl+C и SIGTERM отменяют контекст выполнения.

Версии и блокировку между процессами по-прежнему ведёт golang-migrate.
После ошибки миграция остаётся помеченной dirty, даже если её изменения
отменены. Повторный запуск не сбрасывает этот признак автоматически:
сначала нужно проверить состояние БД и устранить причину сбоя.
